# Подсветка предметов по rank: реверс div.exe 1.0.0.62 (06.11.2026)

Источники: `scratch/re/out/div_all.c` (декомпиляция), `scratch/re/rdis.py A B` (capstone-дизассемблер диапазона VA), `scratch/re/out/q.py ADDR` (функция из декомпиляции). Игру не запускали, `scratch/gfx_pilot_game` и `X:\GAMES` не менялись (читали только список файлов).

## 1. Где хранится rank и откуда цвет названия

### Структуры
- **Экземпляр предмета в мире** — запись 0x6c байт в массиве `[DAT_00658bdc+0x20]` (счётчик `[+0x28]`): `+0x18` short высота, `+0x1c/+0x20` x/y, `+0x24` архетип (индекс в таблицу записей 0x94 по `[DAT_00658bdc+0x1c]`; `rec+0x1c & 0x800` = подбираемый предмет, `rec+0x34` = категория вкладки), `+0x28` индекс спрайта, `+0x30` флаги, `+0x34..+0x44` битовое поле (читается `FUN_005918b0(ptr, flags, N)` / `FUN_00591920`). Флаги `+0x30`: `0x80000` = у предмета есть «ссылка» (ItemLink, особые свойства), `0x100000` = ссылка уже создана, `0x40000000` = предмет-особый, `0x8` = есть счётчик.
- **Запись предмета в рюкзаке/на кукле** — 0x28 байт, тот же набор полей со сдвигом: `+0 x, +4 y, +8 архетип, +0xc контейнер (-1 = рюкзак), +0x10 short количество, +0x14 флаги (те же биты), +0x18 битовое поле`. Доступ: `FUN_00414e90(ecx=инвентарь, i)` вернёт указатель на запись (вектор `{данные, число, шаг}` по `[inv+4]`).
- **ItemLink-объект** (RTTI `.?AVCItem@@`, файл `WORLD\ItemLink.cpp`): менеджер — глобал `0x750cfc`, массив `[mgr+0x24]`, число `[mgr+0x28]`. Получение: `FUN_0057a970` (thiscall, `ecx=0x750cfc`, стек: `arch, &flags, create, force`, `ret 0x10`). Возвращает 0, если нет бита `0x80000`; если бита `0x100000` нет, а `create=0` — тоже 0 (ссылка не создана); `create=1,force=0` — генерирует предмет (`FUN_0057a5e0`), `force=1` — создаёт копию шаблона с `rank=0`.
- **RANK** = `*(int*)( *(int*)(link+0x84) + 0x90 )` (32-битное целое, 0..5). Подтверждено: при создании копии `*(link+0x84)+0x90 = 0` (в `FUN_0057a970`), и `switch` по нему в `FUN_0058a720`.

### Таблица rank -> цвет названия (адрес 0x58aa13..0x58aaa3, `jmp [0x58c520+rank-1]`)
`FUN_0058a720` (0x58a720) строит строку названия «`\r<код><имя>`», где код = `esi`: по умолчанию **2**; rank 1 -> **7**, 2 -> **0x11**, 3 -> **0x25**, 4 -> **0x20**, 5 -> **0x16** (таблица переходов `0x58c520`: `0x58aa87,0x58aa8e,0x58aa95,0x58aa9c,0x58aaa3` -> `mov esi,imm`). Предметы без ссылки (`FUN_0057a970` вернул 0) — всегда код 2 (константа `push 2` в 0x58c1ed/0x58c202).

Код -> шрифт: символ после `\r` в тексте = **индекс шрифта + 1** (разбор в `FUN_004f1170`, отрисовка в `FUN_004f68e0`: `iVar = c - 1`, шрифт `FUN_0045bfe0(index)` из массива `[fontmgr+0x78]`). Порядок загрузки шрифтов — таблица `0x64d558` (строки `fonts\...fnt`, 5 размеров на цвет, подтверждено заглушкой Simsun `FUN_00496c90` с теми же цветами): индексы 0–4 `fontn1..5` (белый), 5–9 `fontgra` (серый), 10–14 `fontred`, 15–19 `fontb` (синий), 20–24 `fontgo` (золотой c8c840), 25–29 `fontor` (оранжевый ff7f00), 30–34 `fontyel` (жёлтый), 35–39 `fontgr` (зелёный), 40–41 `fontblack1,2`, 42–44 `fontbig24`..., 45–47 `fontbig36`, 48–51 `dialog_*`. Итог для размера 2: rank0 `fontn2` (код 2), 1 `fontgra2` (7), 2 `fontb2` (17), 3 `fontgr2` (37 = `%`), 4 `fontyel2` (32 = пробел), 5 `fontgo2` (22). Файла `fontlist.txt` в игре нет (`FUN_0045bf90` берёт встроенный список).
Формат-строка `"\r%c%s"` = `0x607f80`; сами символы 0x20/0x25 безопасны: код передаётся как аргумент `%c`, а не как формат.

### Вывод для ChatGPT-разведки
Цвет по rank — **уже есть в движке** для всех мест, где название строит `FUN_0058a720` (подсказка, Alt-подпись). Перекрашивать шрифты не нужно; для подсветки ореолом rank читается так: `link = FUN_0057a970(arch, &flags, 0, 0)`; `rank = link ? *(*(link+0x84)+0x90) : 0`.

## 2. Alt-подписи на земле

- Алгоритм: `FUN_004a5190` (0x4a5190, `ecx` = игровой контроллер). Условие: `GetAsyncKeyState(0x12)` (0x4a51bf) и `FUN_00527140(2)`. Цикл по видимым узлам `DAT_00658be4` (`[+0x3a]&1` = предмет, `[+0x38]` = id экземпляра). Предмет показывается, если `rec+0x1c & 0x800` (или арх. 0x14af, или `rec[0]&0x20` в режиме 1). Для каждого: `FUN_004a43a0(id)` (загрузка записи экземпляра) -> `FUN_0058a720(ecx=0x658bdc, hero, inst, buf, 0, x, y, z)` (**0x4a5306**) -> `FUN_004f1a50(&0x6e00f0, x, y, 0xfffffcae, шрифт.., fmt "%s" 0x607f7c, buf)` (0x4a5392) -> текстовый блок (`FUN_004f1770`, `MISC\boxes.cpp`).
- Шрифт подписи выбирается ВНУТРИ строки (`\r<код>`), т.е. цвет по rank уже учтён. **Но**: `FUN_0058a720` вызывает `FUN_0057a970(.., create=0, ..)`, поэтому у предметов, которые игрок ещё не наводил мышью (нет бита `0x100000`), ссылки нет -> подпись белая. Hover-функция `FUN_004a4700` (0x4a50a1..0x4a50da) предварительно создаёт ссылку: `FUN_0057a970(arch,&flags,1,0)` и `FUN_00581ed0(inst)` (запись в файл-кэш), после чего подсказка цветная.
- **Патч (написан и проверен Unicorn):** `games/divine-divinity/patch_research/alt_color_patch.py` — в цикле Alt после `call 0x4a43a0` (0x4a5280) выполняется та же генерация. Точка вставки 0x4a5285 (`mov edx,[0x75182c]` 6 байт -> `call 0x605ba0; nop`), пещера 0x605ba0 (62 байта в хвосте `.text`; 0x605b70..0x605b98 занят патчем анимации, зону 0x605ba0..0x605bff он не трогает). Выход `scratch/re/div_patched_glow.exe` (sha256 28b11d5e...b184). Эмуляция: 12 комбинаций флагов x результат генерации — 0 расхождений (вызов `0x57a970` с аргументами `(arch,&inst+0x30,1,0)`, запись `0x581ed0`, edx = `[0x75182c]`, ebx/esi/edi/ebp сохранены, стек сбалансирован). В игре НЕ запускался.
- Побочный эффект/риск: предметы получают свои свойства в момент нажатия Alt, а не при первом наведении (rand-последовательность иная, но механизм тот же, что у hover). Проверить в игре: цвет подписей rank 1–5, нет «зависания» при Alt в толпе предметов, сохранение/загрузка (флаг 0x100000 пишется в кэш, как при hover).

## 3. Отрисовка спрайтов предметов

Формат спрайта (общий, `FUN_00556a80`): `+8` short ширина, `+10` short высота, с `+0xc` строки: `short nSpans; int pixelPtr (абсолютный указатель на RGB565-пиксели строки); nSpans x {short x, short len}; short pad` — шаг строки в шортах `2*n+4`. Маска спрайта = объединение спанов (отдельный alpha не нужен). Поверхность — RGB565 (`pitch = (W+extra)*2`). Общий блит: `FUN_00556a80(dst, sprite, W, H, x, y, extra)` (cdecl, 7 аргументов, `add esp,0x1c`); при `DAT_006e02a0 != 0` копирует через `FUN_0044dc60` (другой режим, формат не выяснен).

### 3a. Рюкзак/сундук/торговля — `CBMCInventoryViewer` (FUN_005226e0, `ecx`=viewer)
- Модель: `[viewer+0x58]` (vtable `0x61972c` для игрока: `+8` число, `+0xc` = `FUN_00521210` «дать i-й предмет», `+0x10` hover, `+0x14` бросок `FUN_00521390`); `[model+0x14]` = инвентарь, `[model+4][i]` = индекс спрайта (арх. 0).
- Цикл по i (счётчик `[esp+0x1c]`, предел `[esp+0x2c]`), `edi` = viewer. Блит предмета: **`call 0x556a80` на 0x52294b** (аргументы кладутся 0x522926..0x52294a: `dst=clip.ptr+..`, `sprite`, `W`, `H`, `x`, `y`, `extra`). Счётчик (>1) рисуется шрифтом 4 (0x5229b3). Подсветка наведения — пульсирующее кольцо `CPulsatingRingTransformation` (0x522842).
- Доступ к rank из пещеры на 0x52294b: `i = [esp+0x38]` (внутри пещеры после `call`: `[esp+0x1c]+0x1c+4`), `edi` = viewer -> `inv = [[edi+0x58]+0x14]` -> `entry = FUN_00414e90(inv, i)` -> `flags = entry+0x14`, `arch = [entry+8]` -> `FUN_0057a970`. Аргументы блита (спрайт `[esp+8]`, W/H/x/y/extra `[esp+0xc..0x1c]`) доступны на стеке — маска и поверхность есть.

### 3b. Кукла (окно экипировки) — `CShieldPlate` (shieldpl.cpp), draw = vtable `0x619ae4+0x38` = **FUN_00529c10**
- 11 слотов (`edi` 0..10): спрайт слота `[this+0xe4+slot*4]` (-1 = пусто), кадр/арх. `[this+0x110+slot*4]`, позиция `[this+0x34+slot*4]+3` (x), `[this+0x60+slot*4]+dy` (y), `entry = FUN_00422260(ecx=[this+0x174], slot)` (в `ebp`!, запись 0x28 байт, как в рюкзаке), `ebx` = поверхность `*param_2`.
- Рисует через виртуальный метод поверхности `call edx` (vt+0x28), 8 аргументов, спрайт = `FUN_004e9850([this+0xe4..],[this+0x110..])->+8`: **0x529d87** (обычный слот) и **0x529dd5** (слот, не подходящий по требованиям; затем запись hover-данных в 0x7454a4..0x7454b4). Игра сама уже читает ссылку для слота: `FUN_0057a970([ebp+8], ebp+0x14, 0, 0)` (0x529d27). Значит `ebp` в обоих местах = запись предмета -> rank доступен без доп. поиска. Что делает vt+0x28 (внутри вероятно тот же `556a80` с клипом) — не раскрыто; безопаснее вставлять ореол отдельной своей процедурой с теми же x, y и маской спрайта.

### 3c. Предметы в мире
- Построение очереди: `FUN_0059e200` (цикл по экземплярам 0x6c, режим Alt: `if (Alt && flags&0x20/0x10000000) node+0x20 |= 0x100`, 0x59e..); готовый узел (`node = inst[0x1a]`) кладётся `FUN_00546770` (SORTSPR\sortspr.cpp). Узел: `+4` ссылка на спрайт-данные, `+8/+0xc` x/y, `+0x20` флаги, `+0x24` обработанный спрайт (`FUN_004903a0`), `+0x28` кадр, `+0x2c` прозрачность 0..255 (`0xff - inst[0x4e]`), `+0x38` ushort id экземпляра (`inst = [0x658bdc+0x20] + id*0x6c`), `+0x3a` бит 1 = предмет/интерактивный, `+0x50..` габариты.
- Отрисовка узла: `FUN_005468a0` (thiscall `ecx`=узел): единственный вызов **внешней DLL** `Slashed` (глобал `DAT_00746a58` = объект из `DllSlashedGetInfo(0)`, vtable[+0x20]) — **`call edx` на 0x5469ca**, 18 аргументов (спрайт `node+0x24` либо `[node+4]+8`, x, y, флаги `(short)uVar1`, `node+0x2c` — прозрачность и т.д.). В самой DLL (slashN.dll, не декомпилирована) идёт реальная растеризация мира; DD сортировка/глубина уже учтены порядком вызовов `FUN_00546a70` (массив узлов в `sortspr`).
- Вывод: ореол мира проще всего вставлять в 0x5469ca как ДОПОЛНИТЕЛЬНЫЙ вызов `Slashed.vt+0x20` перед основным, но с другим «спрайтом» (предрассчитанный glow-силуэт цвета rank из архива, в который GameRemix положит по индексу+блоб) и узловой прозрачностью ~0x60..0x80 — глубина и позиция совпадают с предметом. Это не требует кода масок в exe. Риск: смысл флагов `uVar1` (низ. биты 2/4/0x10...) и поведение прозрачности в DLL не проверены; нужен отладочный прогон на копии.

## 4. План патча

1. **Готово: цветные Alt-подписи** — `alt_color_patch.py` (раздел 2). Следующие шаги — проверка в игре владельцем (копия `scratch\gfx_pilot_game`) на предметах разных рангов.
2. **Ореол в рюкзаке (рекомендуемый первый ореол).** Пещера вместо `call 0x556a80` на 0x52294b (`e8 rel32` -> `call cave`): (а) `rank` по цепочке из 3a (+ кэш rank не нужен: `FUN_0057a970` дешёвая); (б) если rank 0 -> `jmp 0x556a80`; иначе вызвать собственную `halo(dst, sprite, W, H, x, y, extra, color565)`: для смещений кольца (радиус 1–2, 8–12 точек) пройти спаны спрайта и подмешать цвет в `dst` (RGB565: `((d & 0xF7DE)>>1) + ((c & 0xF7DE)>>1)` — 50% смешивание без переносов; для мягкости второй проход с радиусом 2 и `>>2`) с клипом по W/H (формат `556a80` образец); затем `jmp 0x556a80` (собственно предмет закрывает середину). Кэш масок не нужен: спрайты 20–45 px, предметов в рюкзаке десятки. Предрасчёт по индексу спрайта нужен только если нагрузка окажется заметной. Таблица цветов rank->RGB565 задать в пещере (в нашей палитре: серый 0x8410, синий 0x421F, зелёный 0x07E0, жёлтый 0xFFE0 (владелец хотел фиолетовый для rank 4 — подставить 0xA81F), золотой 0xFD20).
3. **Кукла**: та же `halo` перед двумя вызовами vt+0x28 на 0x529d87/0x529dd5 (нужен dst-указатель поверхности — взять из структуры `*param_2` (поля: `[0]` ptr, `[4]`/`[8]` смещения, `[0xc]`/`[0x10]` размеры, `[0x14]` pitch, как в 0x5226e0: `piVar1`), x/y = слоты `+0x34/+0x60`). Нужно проверить, что vt+0x28 принимает те же координаты, что и `556a80` (иначе повторить расчёт 0x5226e0).
4. **Земля**: дополнительный вызов в 0x5469ca с glow-спрайтом (см. 3c) — самый сложный пункт; сначала экспериментальный прогон одного вызова на копии игры.
5. Конфиг/меню GameRemix: включение, цвет по rank, интенсивность; хранить в секции таблицы в пещере (патч задаёт константы при применении).

## 5. Открытые вопросы
- Формат поверхности: 565 или 555 (`DAT_006e02a0`, `FUN_0044dc60` — альтернативная ветка блита).
- Что делает vt+0x28 у поверхности `CShieldPlate` и можно ли звать `556a80` напрямую на слоте.
- Параметры `Slashed.vt+0x20`: флаги, прозрачность, нужен ли отдельный спрайт-ореол.
- Предметы на персонаже и у NPC (не предметы мира) — вне задачи.
